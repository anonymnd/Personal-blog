You have written a clean JPA repository method, but your application feels sluggish. You suspect that Hibernate is executing hundreds of queries for a single request, but since the SQL is hidden behind the abstraction layer, you are essentially flying blind. Understanding how to read these logs is the only way to verify if your fetch plans are working as intended.

## Enabling the SQL Output
To see what is happening under the hood, you must configure your `application.properties`. Setting `spring.jpa.show-sql=true` prints the SQL to the console, but it is often unreadable. To make it useful, use `spring.jpa.properties.hibernate.format_sql=true` for pretty-printing and `logging.level.org.hibernate.orm.jdbc.bind=trace` to see the actual values being bound to the parameters.

## Interpreting the Log Pattern
When you look at the logs, you will see a pattern: a `SELECT` statement followed by several `binding parameter` lines. Hibernate uses prepared statements for security and performance. Instead of putting values directly in the SQL, it uses placeholders (?). The trace logs tell you exactly which value replaces which placeholder. If you see a long sequence of similar SELECT statements for different IDs, you have likely encountered the N+1 problem.

## Worked Example: Procurement Requests
Imagine a procurement app where a `PurchaseRequest` has many `RequestItem` entities. If you fetch 10 requests and then loop through them to print the items, the logs will show:

```sql
-- 1 query to get requests
SELECT * FROM purchase_request;
-- 10 additional queries to get items for each request
SELECT * FROM request_item WHERE request_id = 1;
SELECT * FROM request_item WHERE request_id = 2;
... (and so on)
```
This confirms a Lazy Loading issue. The fix is using a `JOIN FETCH` in your JPQL to consolidate this into one single query.

## Common Mistake: Over-reliance on EAGER
Developers often see these logs and immediately change `@OneToMany` to `fetch = FetchType.EAGER`. This is a mistake because it forces Hibernate to load the collection every single time, even when not needed, which can crash your app as the database grows. The correct approach is to keep it `LAZY` and use specific fetch joins for specific use cases.

## Practical Exercise
If you see `binding parameter [1] as [101]` followed by a `SELECT` on a table called `request_item`, what does this tell you about the query?

**Answer:** Hibernate is executing a query to find items associated with the specific ID 101.
