Imagine you are building a procurement system where a requester submits a purchase request. A common struggle for beginners is deciding whether to send the entire database entity or a tailored object. Sending raw entities often leaks internal database IDs or sensitive fields, while overly generic objects make the API ambiguous.

## Separating Entities from DTOs
To avoid leaking internal logic, use Data Transfer Objects (DTOs). A Request object defines exactly what the client must provide, while a Response object defines what the server promises to return. For a procurement request, the `PurchaseRequestRequest` might only need `itemName` and `quantity`, whereas the `PurchaseRequestResponse` includes the `requestId` and `status` generated by the server.

## Structuring the Request Object
Request objects should be lean. Avoid including fields that the server should determine, such as timestamps or primary keys during creation. If a manager is approving a request, the request object should focus on the action (e.g., `approvalStatus` and `comments`) rather than repeating the entire order details.

## Designing the Response Object
Responses should be predictable. Instead of returning a simple string, use a structured object. This allows you to add metadata later without breaking the client. For a successful creation, return the created object and a `201 Created` status with a `Location` header.

## Worked Example: Procurement Submission
Here is an illustrative excerpt of how these objects look in a Jakarta-based API:

```java
// Request Object
public class ProcurementRequestDTO {
    private String itemDescription;
    private Integer quantity;
    // Getters and Setters
}

// Response Object
public class ProcurementResponseDTO {
    private Long requestId;
    private String status;
    private LocalDateTime createdAt;
    // Getters and Setters
}
```
If a user submits a request, the server processes the `ProcurementRequestDTO` and returns a `ProcurementResponseDTO` with a `201` status, confirming the ID is now `101` and the status is `PENDING`.

## Common Mistake: The Universal Object
Developers often create one `ProcurementDTO` for both creating and updating. This is a mistake because `id` is required for updates but forbidden for creation. 
**Correction:** Create separate `CreateRequestDTO` and `UpdateRequestDTO` to enforce strict validation.

## Practical Exercise
Design a response object for a 'Buyer' who just ordered an item. What fields are essential?

**Check:** It should include the `orderId`, `trackingNumber`, and `orderDate`. It should not include the buyer's internal password hash.
