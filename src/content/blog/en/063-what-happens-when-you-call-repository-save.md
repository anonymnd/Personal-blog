Imagine you are building a procurement app. A requester submits a purchase request, and you call `repository.save(request)`. You might assume this immediately sends an `INSERT` statement to the database, but the reality is more nuanced. The `save()` method is a high-level abstraction that hides a decision process based on the entity's state.

## How Spring Data decides between persist and merge
With the default new-entity detection, Spring Data first checks a non-primitive version property when available: a null version marks an entity as new. Otherwise it checks whether the identifier is null. A class implementing `Persistable` can supply its own `isNew()` decision. New entities are passed to `EntityManager.persist()`; others to `merge()`. This is not a database existence check, and `merge()` can result in an insert as well as an update. For a detached object, merge copies state into a managed instance rather than attaching that original object.
## The return value and transaction lifetime
For a detached entity, use the instance returned by `save()` rather than expecting the original object to become managed. If the input is already managed, merge can return that same managed instance. Also check the transaction boundary: when only the repository's own transaction is used, it may have finished before control returns to your caller, so even the returned object is no longer managed there. Within an outer service transaction, managed changes can be detected until that persistence context ends. A returned object is not a promise of unlimited automatic saving.
## Timing of the SQL Execution
Calling `save()` does not always trigger immediate SQL. JPA uses a 'write-behind' strategy. It queues changes in the Persistence Context and only flushes them to the database when necessary (e.g., before a query or when the transaction commits). However, if you use `@GeneratedValue(strategy = GenerationType.IDENTITY)`, Hibernate must execute the `INSERT` immediately to retrieve the ID generated by the database.

## Worked Example: Procurement Request
```java
// Creating a new request
PurchaseRequest req = new PurchaseRequest("Laptop", 1200.00);
PurchaseRequest savedReq = repository.save(req); 
// Outcome: persist() called -> INSERT executed (if IDENTITY)

// Updating the request
savedReq.setStatus("APPROVED");
PurchaseRequest updatedReq = repository.save(savedReq);
// Outcome: merge() called -> UPDATE executed during flush
```

## Common Mistake: The Detached Entity
**Mistake:** Calling `repository.save(entity)` and then continuing to modify the `entity` object instead of the returned result.
**Correction:** Always assign the result: `entity = repository.save(entity);`.

## Practical exercise
An entity has an assigned, non-null ID, no nullable version property, and no custom `Persistable.isNew()` implementation. Under default detection, does save call persist or merge?

**Answer:** Merge. That choice alone does not establish whether the resulting SQL will be an INSERT or UPDATE; entity state and database contents still matter.
