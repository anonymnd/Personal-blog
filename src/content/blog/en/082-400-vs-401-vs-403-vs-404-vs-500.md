Imagine you are building a procurement app. A requester tries to submit a purchase request, but the server returns a generic error. Without specific status codes, the frontend doesn't know if the user forgot a field, isn't logged in, or if the database crashed. This ambiguity leads to poor user experiences and slow debugging.

## Client-Side Errors (4xx)

HTTP 4xx codes indicate that the client sent a request that the server cannot process. The most common is **400 Bad Request**, used when the request payload is syntactically incorrect. For example, if the procurement app expects a numeric `quantity` but receives a string "ten", a 400 is appropriate.

**401 Unauthorized** and **403 Forbidden** are often confused. A 401 means the server doesn't know who you are (authentication). It usually includes a `WWW-Authenticate` header. A 403 means the server knows who you are, but you don't have permission (authorization). In our app, a requester might be authenticated (200 OK) but forbidden (403) from approving their own request.

**404 Not Found** occurs when the requested resource doesn't exist. However, APIs sometimes return a 404 instead of a 403 to hide the existence of a sensitive resource from unauthorized users.

## Server-Side Errors (5xx)

**500 Internal Server Error** is the catch-all for when something goes wrong on the server that isn't the client's fault. This could be an unhandled null pointer exception in the Java backend or a lost database connection. Unlike 4xx codes, a 500 indicates the server failed to fulfill a valid request.

## Worked Example: Procurement Workflow

Consider a `PUT /requests/{id}/approve` endpoint:
- **Scenario A**: Request body is missing the `managerId`. Result: `400 Bad Request`.
- **Scenario B**: No Bearer token provided in the header. Result: `401 Unauthorized`.
- **Scenario C**: A regular employee tries to call the approve endpoint. Result: `403 Forbidden`.
- **Scenario D**: The request ID `999` does not exist. Result: `404 Not Found`.
- **Scenario E**: The server throws a `RuntimeException` during the update. Result: `500 Internal Server Error`.

## Common Mistake: 401 vs 403

A frequent error is returning a 401 when a user is logged in but lacks permissions. 
*Correction*: Use 401 only for missing or invalid credentials. Use 403 when the identity is verified but the action is prohibited.

## Practical Exercise

If a user tries to access `/orders/55` but they are not logged into the system at all, which status code should the API return?

**Answer**: 401 Unauthorized.
