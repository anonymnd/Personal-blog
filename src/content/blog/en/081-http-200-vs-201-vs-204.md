Imagine you are building a procurement system. A requester submits a purchase request, and your API returns a success message. But does 'success' mean the request was simply received, that a new record was created, or that an update happened without needing to send data back? Using a generic 200 OK for everything makes it hard for the frontend to know if it should redirect the user or just refresh a list.

## Understanding HTTP 200 OK
HTTP 200 is the standard response for successful HTTP requests. It is most commonly used with GET requests to return a resource representation or with PUT/PATCH requests when the server sends back the updated object. It tells the client: "I processed your request, and here is the result."

## The Specificity of HTTP 201 Created
While 200 means 'OK', 201 specifically means 'Created'. This is primarily used with POST requests. When a requester submits a new purchase request in our app, the server doesn't just say OK; it confirms a new resource exists. Ideally, a 201 response includes a `Location` header pointing to the URL of the newly created resource.

## The Silence of HTTP 204 No Content
HTTP 204 is used when a request is successful, but there is no representation to return to the client. This is common for DELETE requests or PUT updates where the client already has the data and doesn't need the server to send the same object back. It saves bandwidth by omitting the response body entirely.

## Practical Example: Procurement Workflow

| Action | Method | Expected Code | Reason |
| :--- | :--- | :--- | :--- |
| View Request | GET | 200 OK | Returns the request details |
| Submit Request | POST | 201 Created | New request record created |
| Update Status | PATCH | 204 No Content | Status changed, no body needed |

```http
POST /api/purchase-requests
Content-Type: application/json

{"item": "Laptop", "qty": 1}

HTTP/1.1 201 Created
Location: /api/purchase-requests/123
```

## Common Mistake: Overusing 200 OK
Developers often return 200 OK for everything. For example, returning 200 after a POST creation instead of 201. This forces the client to parse the response body to determine if a resource was actually created, rather than relying on the semantic meaning of the HTTP status code.

## Practical Exercise
Which status code should a manager's 'Approve' action return if the API updates the request status to 'Approved' but does not return the updated object in the body?

**Answer:** 204 No Content.
