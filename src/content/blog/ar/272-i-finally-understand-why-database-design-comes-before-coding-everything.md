هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخايل معايا بديتي كتصاوب تطبيق ديال المشتريات (procurement app) وبديتي نيشان كتكتب الكلاصات ديال Java لـ `PurchaseRequest`. صاوبتي الحقول، درتي الـ REST controller وبديتي ف اللوجيك. من بعد جوج سيمانات، عاد اكتشفتي بلي طلب واحد خاصو يهز بزاف ديال السلع، وكل وحدة عندها ضريبة مختلفة. هنا غتلقى راسك بلي كاع داكشي لي كوديتي ف الـ service layer خاصو يتبدل حيت الداتا لي صاوبتي ف الأول كانت بسيطة بزاف وماكتسدش هاد الاحتياجات. هادشي هو لي كنسميوه 'فخ الكودينغ قبل التصميم'.

## مثال ديال البلان
باش تكودي بلا ما يكون عندك schéma ديال database، بحال إلا بنيتي الحيوط ديال الدار قبل ما تعرف فين غيدوزو القوادس ديال الماء. الـ database هي الساس ديال التطبيق. إلا كان الساس عوج، أي سطر ديال الكود كتبتي فوق منه غيكون غير 'ترقيع'. ملي كنصممو الـ schema هو الأول، كنقدرو نشوفو القواعد ديال البيزنس—مثلاً واش `Buyer` واحد يقدر يتكلف بزاف ديال `Orders`—قبل ما نحبسو راسنا ف واحد الطريقة ديال الكودينغ.

## كيفاش كنرسمو تدفق المشتريات
ف تطبيق افتراضي ديال المشتريات، الداتا هي لي كتحكم ف اللوجيك. إلا رسمناها هي الأولى، غنبانو لينا تلاتة ديال الحاجات أساسية: `Request` (الطلب)، `Approval` (الموافقة)، و `PurchaseOrder` (أمر الشراء).

| Entity | العلاقة | الشرط |
| :--- | :--- | :--- |
| Request | 1:N مع Approval | خاصو على الأقل موافقة وحدة باش يدوز |
| Request | 1:1 مع PurchaseOrder | كل طلب مقبول كيعطي أمر شراء واحد |
| User | 1:N مع Request | المستخدم يقدر يدير بزاف ديال الطلبات |

## مثال تطبيقي
إلا صاوبنا الـ schema هي الأولى، غنديرو جدول لـ `Request` وجدول لـ `RequestItem`. ف Jakarta Persistence، الكود غيكون بحال هكا:

```java
@Entity
public class Request {
    @Id @GeneratedValue
    private Long id;
    private String description;
    
    @OneToMany(mappedBy = "request")
    private List<RequestItem> items;
}
```
ملي كنعرفو بلي كاين `@OneToMany` من الدقة الأولى، المبرمج كيعرف كيفاش يكتب الميثود ديال `saveRequest` باش تقبل ليستة ديال السلع بلا ما يتفاجأ من بعد.

## غلط شائع: 'الجدول الشامل'
بزاف ديال الناس كيديرو غلط ديال جدول واحد كبير (مثلاً `ProcurementData`) فيه كلشي: لي طلب، لي وافق، السلعة، والثمن. هادشي كيدير تكرار ديال الداتا وكيصعب التعديل. الحل هو **Normalization**: نقسمو الداتا لجداول منطقية ونربطوهم بـ foreign keys.

## تمرين تطبيقي
سيناريو: بغيتي تزيد 'صنف' (Category) بحال (إلكترونيك، أدوات مكتبية) للسلع. واش تزيد `category_name` كـ string ف كل `RequestItem` ولا تصاوب جدول `Category` بوحدو؟

**الجواب:** خاصك تصاوب جدول `Category` بوحدو وتربطو بـ foreign key باش تفادى الأخطاء ف الكتيبه وتسهل تغيير السمية ديال الصنف ف كاع الطلبات دقة وحدة.
