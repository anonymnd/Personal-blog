هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخايل راسك كتصاوب تطبيق ديال المشتريات (procurement app). بديتي نيشان كتكتب الكلاس `PurchaseRequest` وكتصاوب la base de données. من بعد جوج سيمانات، عاد اكتشفتي بلي manager ماشي غير كايوافق (approve)، ولكن يقدر يرجع الطلب باش يتصحح (revision) أو يصيفطو لmanager آخر. حيت بديتي بالكود، دابا خاصك تعاود كلشي من الزيرو فـ data model والمنطق ديال الخدمة.

## الفخ ديال التطبيق المباشر
بزاف ديال المبتدئين كايسحاب ليهم بلي البرمجة هي أهم حاجة فـ software engineering. ولكن فالحقيقة، الكود هو غير الترجمة الأخيرة ديال الحل. ملي كاتبدا بالكود، كتكون غير كاتخمن المتطلبات وفنفس الوقت كتحاول تحل المشاكل التقنية. هادشي كايخليك تركز على تفاصيل صغيرة وتصاوب functions ما عندها حتى معنى حيت ما فهمتيش القاعدة ديال البيزنس مزيان.

## ركز على النتيجة اللي بغا المستخدم
قبل ما تحل IDE ديالك، حدد شنو هي النتيجة النهائية. فالتطبيق ديالنا، النتيجة ماشي هي « table فـ base de données »، ولكن هي « الموظف يوصل للحاجة اللي طلبها ». ملي كتوضح النتيجة، حدد القواعد: شكون اللي يقدر يطلب، شكون اللي كيوافق، وشنو كيوقع إلا فات الميزانية.

## طريقة الـ Vertical Slice
عوض ما تبني architecture كاملة، ركز على طرف صغير (vertical slice). حدد مسار بسيط: الموظف كيصيفط → manager كيوافق → المشتري كيطلب السلعة. دير شروط قبول (acceptance criteria) لهاد الطرف (مثلا: « manager خاصو يوصلو notification ملي يتصيفط الطلب »).

## مثال تطبيقي: الطريقة الغالطة مقابل الصحيحة

**الطريقة الغالطة:**
```java
// كبدا بـ entity عامة بلا قواعد واضحة
public class Request {
    private Long id;
    private String status; // "PENDING", "APPROVED"
    // ... getters and setters
}
```
*النتيجة:* نسيتي الحالة ديال « Revision » وخاصك دابا تبدل la base de données كاملة.

**الطريقة الصحيحة:**
1. **النتيجة:** مسار الموافقة على الطلبات.
2. **القاعدة:** الطلبات تقدر تكون: مقبولة، مرفوضة، أو محتاجة تصحيح.
3. **الكود:** طبق غير المنطق اللي كيحتاج هاد التلاتة ديال الحالات.

## غلط شائع: تعقيد الـ Architecture
بزاف كايحاولوا يصاوبوا architecture « مثالية » و scalable قبل ما يعرفوا القواعد ديال البيزنس. الـ architecture خاصها تكون iterative. بدا ببساطة، وطور التصميم على حساب شنو كايطلب منك البيزنس.

## تمرين تطبيقي
طلبوا منك تزيد ميزة « تنبيه الميزانية » (Budget Alert). بلا ما تكتب الكلاس `AlertService` دابا، كتب جوج قواعد ديال البيزنس وشرط قبول واحد.

**التصحيح:**
*القاعدة 1: التنبيه كيخدم إلا كان الطلب > 1000$. القاعدة 2: غير المسؤول المالي اللي كتوصلو alert. شرط القبول: تأكد بلي طلب ديال 500$ ما كايصيفط حتى notification.
