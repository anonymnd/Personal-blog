تخيل راسك خدام على تطبيق ديال المشتريات (procurement app). دوزتي ساعات وأنت كتكتب الكود باش الـ requester يقدر يصيفط طلب شراء. فجأة، درتي شي تغيير اللي خسر ليك الخدمة كاملة، ولقيتي راسك نسيتي كيفاش كان الكود هادي 20 دقيقة. هنا فين كتحتاج version control، ولكن بزاف ديال المبتدئين كيخلطو بين الأداة اللي كتحفظ الخدمة والبلاصة فين كنحطو ديك الخدمة.

## فهم Git كأنه الموطور
Git هو نظام distributed version control كيكون محطوط عندك فـ PC (local). هو عبارة على برنامج كتـinstalle-يه فجهازك، وهو اللي كيتتبع التغييرات ديال الملفات وكيدير ليها 'snapshots' اللي كنسميوهم commits. حيت هو distributed، كل مطور عندو نسخة كاملة من التاريخ ديال المشروع فـ PC ديالو. يعني ماشي ضروري تكون كونيكطي باش دير commit، ولا تفتح branch جديدة، ولا ترجع لنسخة قديمة من الكود.

## فهم GitHub كأنه المركز (Hub)
GitHub هو خدمة فالسحاب (cloud service) كتهز لينا لي dépôts ديال Git. إذا اعتبرنا Git بحال شي برنامج ديال الكتابة كيسجل التغييرات، GitHub هو بحال Google Drive ولكن خاص بـ Git. كيعطينا واجهة سهلة (GUI)، وتسيير ديال المستخدمين، وأدوات ديال التعاون بحال Pull Requests. Git كيتكلف بالجانب التقني ديال النسخ، و GitHub كيخلي الـ manager يراجع الكود قبل ما يتزاد فالمشروع الأساسي.

## مثال تطبيقي: مسار طلب الشراء
نفترض أنك خدام على الكلاس `RequestService.java`:

1. **عملية محلية (Git):** كتكتب الكود وكتدير `git commit -m "Add request logic"`. هنا الخدمة تسجلات غير فـ PC ديالك.
2. **عملية بعيدة (GitHub):** كدير `git push origin main`. هنا كطلع داك الـ commit من PC ديالك للسيرفر ديال GitHub باش يشوفوه صحابك.
3. **تعاون (GitHub):** الـ lead developer كيحل Pull Request فـ GitHub باش يراجع التغييرات ديالك قبل ما يدمجهم.

## غلط شائع: "GitHub طايح، ماقدرتش ندير commit"
بزاف كيسحاب ليهم بلي إلا ماكاينش الأنترنيت أو GitHub طايح، مايمكنش يسجلو خدمتهم. هذا غلط. حيت Git محلي، تقدر تبقى تـcommit-ي وتصاوب branches وتدمجهم فـ PC ديالك عادي. GitHub كنحتاجوه غير باش نشاركو الكود أو نديرو ليه backup.

## تمرين تطبيقي
