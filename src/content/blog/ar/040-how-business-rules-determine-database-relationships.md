هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخيل راسك كتصاوب سيستيم ديال الشراء (procurement). عارف بلي خاصك 'الموظفين' (Employees) و 'طلبات الشراء' (Purchase Requests)، ولكن حاير: واش الموظف الواحد يدير طلب واحد ولا بزاف؟ هنا فين كيغلطو بزاف ديال المبتدئين؛ كيبغيو يرسمو الـ Database قبل ما يفهمو قواعد البيزنس (Business Rules). فالتصميم ديال قواعد البيانات، القاعدة ديال البيزنس هي اللي كتحكم فـ la cardinalité.

## من قاعدة البيزنس لـ la Cardinalité

قاعدة البيزنس هي شرط محدد على كيفاش الداتا كتعامل مع بعضياتها. مثلاً: 'الموظف اللي طلب يقدر يدير بزاف ديال الطلبات، ولكن كل طلب خاصو يكون ديال موظف واحد'. هاد القاعدة كتعطينا علاقة One-to-Many (1:N). ولكن إلا تبدلات القاعدة وولات 'الطلب يقدر يسنيوه بزاف ديال الموظفين'، هنا كتولي العلاقة Many-to-Many (M:N).

## التعامل مع الاختيارية (Optionality)

ماشي كاع العلاقات ضرورية (mandatory). شوف مثلاً دور 'المدير' (Manager) فالتطبيق ديالنا. ضروري كل طلب يكون عندو موظف اللي طلبو، ولكن ماشي ضروري كل طلب يكون داز عند المدير دابا. هادي هي الـ 'optionality'. فالموديل ديالك، هادشي كيعني أن الـ foreign key ديال المدير يقدر يكون null، ولكن الـ ID ديال الموظف خاصو يكون NOT NULL.

## علاش كنحتاجو Join Entities

ملي كتلقى علاقة Many-to-Many، بحال 'المشترين' (Buyers) و 'الموردين' (Suppliers) (مشتري واحد كيتعامل مع بزاف د الموردين، ومورد واحد كيبيع لبزاف د المشترين)، ما تقدرش تحط غير foreign key فجدول واحد. هنا خاصك 'join entity'. هاد الجدول الوسيط ماشي غير كيربط بيناتهم، ولكن يقدر يهز معلومات على ديك العلاقة نيتها، بحال 'تاريخ العقد' (Contract Date).

## مثال تطبيقي: سير العمل ديال الشراء

القاعدة: *الطلب كيصيفطو موظف واحد وكيوافق عليه مدير واحد.*

| Entity | Relation | Cardinality | المنطق |
| :--- | :--- | :--- | :--- |
| Employee → Request | يصيفط | 1:N | موظف واحد، بزاف د الطلبات |
| Manager → Request | يوافق | 1:N | مدير واحد، بزاف د الموافقات |

```sql
-- مثال بسيط لجدول الطلبات
CREATE TABLE purchase_requests (
    request_id INT PRIMARY KEY,
    description VARCHAR(255),
    requester_id INT NOT NULL, -- ضروري
    manager_id INT, -- اختياري حتى يوافق المدير
    FOREIGN KEY (requester_id) REFERENCES employees(id),
    FOREIGN KEY (manager_id) REFERENCES employees(id)
);
```

## غلط شائع: التعميم الزايد

بزاف كيديرو كاع العلاقات Many-to-Many غير «باش يحتاطو» إلا تبدلات الخدمة. هادشي كيزيد التعقيد وكيتقّل الـ queries. ديما صاوب الموديل على حساب القاعدة اللي كاين دابا؛ وإلا تبدلات القاعدة من بعد، ديك ساعة دير migration لـ schema.

## تمرين تطبيقي

القاعدة: 'طلب الشراء يقدر يكون فيه بزاف ديال المنتجات، والمنتج الواحد يقدر يكون فبزاف ديال الطلبات'. شنو نوع العلاقة هنا، وشنو خاصك باش تطبقها؟

**الجواب:** هادي علاقة Many-to-Many (M:N). خاصك ضروري جدول وسيط (join entity) بحال `request_items` باش تربط بين `request_id` و `product_id`.
