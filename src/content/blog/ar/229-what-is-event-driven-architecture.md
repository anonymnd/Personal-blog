هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخايل معايا خدام على تطبيق ديال المشتريات (procurement app). فالسيسيتيم العادي، ملي الموظف كيدير طلب شراء، السيسيتيم كيبقى يتسنى المدير يوافق ومن بعد المشتري (buyer) يشري السلعة، كلشي مرتبط فخيط واحد. إلا كان السيرفيس ديال المشتري طافي، العملية كاملة كتحبس. هاد المشكل كيتسمى "tight coupling" وهو اللي كيخلي السيسيتيم تقيل وصعيب يتطور.

## كيفاش كتخدم هاد التقنية
الـ Event-Driven Architecture (EDA) كتحل هاد المشكل باستعمال واحد الوسيط كيتسمى "Event Broker" (بحال Kafka ولا RabbitMQ). بلاصة ما السيرفيس A يعيط نيشان للسيرفيس B، السيرفيس A غير كيصيفط "حدث" (event)—يعني خبر بلي "شي حاجة وقعات"—لهاد الوسيط. السيرفيسات لخرين كيكونوا مشتركين (subscribe) فهاد الأحداث، وملي كيوصلهم الخبر، كيديرو الخدمة ديالهم. هادي كتسمى communication asynchrone، حيت اللي صيفط الخبر مكيجلسش يتسنى الجواب باش يكمل خدمتو.

## مثال ديال تطبيق المشتريات
فالسيسيتيم ديالنا، الخدمة غتكون بحال هكا:
1. **سيرفيس الطلبات**: كيصيفط حدث سميتو `RequestCreated`.
2. **سيرفيس المدير**: كيتسنى `RequestCreated` باش يوافق، وملي كيوافق كيصيفط حدث `RequestApproved`.
3. **سيرفيس المشتري**: كيتسنى `RequestApproved` باش يشري السلعة من عند الفورنيسور.

هنا، إلا كان سيرفيس المشتري طافي، الحدث `RequestApproved` كيبقى محفظ فـ Broker، وملي كيشعل السيرفيس، كياخد الخبر وكيكمل خدمتو عادي.

## مثال تطبيقي: شكل الـ Event
الحدث كيكون غالباً عبارة عن JSON صغير. مثلاً الحدث ديال الموافقة `RequestApproved` غيكون بحال هكا:

```json
{
  "eventId": "evt_123",
  "type": "RequestApproved",
  "payload": {
    "requestId": "req_99",
    "approverId": "mgr_01",
    "timestamp": "2023-10-27T10:00:00Z"
  }
}
```
النتيجة: سيرفيس المشتري كيوصلو هاد الـ JSON، كيشوف `req_99` وكيعرف شنو خاصو يشري بلا ما يحتاج يهضر مع سيرفيس المدير.

## غلط شائع: يسحاب ليك الـ Event كيوصل مرة وحدة
بزاف ديال المبتدئين كيسحاب ليهم بلي الـ event كيوصل مرة وحدة بالضبط. ولكن فالحقيقة، يقدر يوقع مشكل فـ réseau ويصيفط الـ Broker نفس الحدث جوج مرات. إلا ما كانش السيرفيس ديالك **idempotent** (يعني واخا يعاود يعالج نفس الحدث ميديرش عملية شراء ثانية)، غادي تشري نفس البيسي جوج مرات.

**الحل**: خاصك تقيد الـ `eventId` فـ database. قبل ما تخدم، شوف واش هاد الـ ID ديجا داز؛ إلا كان داز، تجاهل الحدث.

## تمرين تطبيقي
إلا بغينا نزيدو "سيرفيس ديال التنبيهات" (Notification Service) باش يصيفط إيميل كلما تكرى طلب، ولا توافق عليه، ولا ترفض، كيفاش غندمجوه فـ EDA؟

**الجواب**: هاد السيرفيس خاصو يشترك (subscribe) فكاع هاد الأحداث الثلاثة (`RequestCreated`, `RequestApproved`, `RequestRejected`) ويصيفط الإيميل على حساب نوع الحدث اللي وصلو.
