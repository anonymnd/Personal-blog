تطبيق الشراء خاصو يسجل الطلب، يوري الحالة ديالو ويعلم المدير. الـ database والـ cache والـ broker كل واحد عندو دور. بدا بأبسط تصميم كيسد الحاجة، وزيد المكونات ملي الفائدة ديالها تستاهل تكلفة التشغيل.
## الساس ديال الداتا: Database
الـ database هي المصدر الموثوق والدائم ديال طلبات الشراء. PostgreSQL يقدر يفرض constraints ويثبت transactions باش الموافقة تبقى مسجلة من بعد restart. السرعة كتبدل حسب queries و indexes والضغط والإعدادات؛ ماشي أي عملية فـ DB كتكون تقيلة غير حيت كاين disk.
## طبقة السرعة: Cache
الـ cache كيحتافظ بنتائج كنعاودو نحتاجوها باش ننقصو الخدمة المكررة. فـ cache-aside، التطبيق كيقلب فالـ cache، وإلا ما لقا والو كيجيب القيمة من DB وكيخزنها فالـ cache. حالة الموافقة تقدر تولي قديمة: خاصنا نمسحوها ولا نبدلوها ملي كتبدل القيمة الأصلية، ونختارو TTL مناسب. Redis يقدر يحفظ الداتا بـ RDB ولا AOF، يعني restart ما كيمسحهاش ديما. فهاد المثال، كنعتابرو الداتا فالـ cache قابلة تتعاود تتبنى.
## مركز التواصل: Message Broker
الـ broker كيفرق اللي كيصيفط الميساج على اللي كيعالجو. من بعد الموافقة، worker يقدر يعالج event بلا ما الطلب يبقى كيتسنى إرسال الإيميل. بقاء الميساجات كيتعلق بالإعدادات و acknowledgements و retention. خاص المستهلك يتعامل مع ميساج جا مرة أخرى بلا ما يصيفط جوج إيميلات؛ outbox يقدر يربط التغيير فـ DB بالنشر اللي غادي يجي من بعد.
## ملخص المقارنة

| الميزة | Database | Cache | Message Broker |
| :--- | :--- | :--- | :--- |
| الهدف الأساسي | التخزين الدائم | السرعة | تفريق الخدمات |
| فين كتخزن | Disk | RAM | Queue/Log |
| مدة البقاء | سجلات دائمة | قيم نقدروا نعاودوا نبنيوها | حسب إعدادات retention |

## غلط شائع: استعمال Redis كـ DB
ما تفترضش أن Redis مصدر دائم غير حيت سريع. فيه persistence، ولكن خاص الإعدادات و eviction وطريقة الاسترجاع يناسبو الحاجة ديالك. فهاد المثال، خلي تاريخ الشراء فـ PostgreSQL وخزن فالـ cache غير القيم اللي تقدر تعاود تجيبها.
## تمرين تطبيقي
أشمن مكون غادي تستعمل باش تعامل مع 10,000 إيميل ديال "تأكيد الطلب" دقة وحدة بلا ما يطيح السيرفر ديال الإيميلات؟

**الجواب:** Message Broker. حيت كيجمع الطلبات فـ queue، وكيخلي سيرفر الإيميلات يخرجهم بشوية عليه على حسب القدرة ديالو.
