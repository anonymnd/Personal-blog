هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخايل راسك خدام على سيستيم ديال الشراء (Procurement). فالبداية، درتي كلشي فبلاصة وحدة. ولكن ملي زدتي ميزات بحال 'الموافقة على الطلب' و 'الطلب من الفورنيسور'، الكود ديالك ولا مرون بزاف. وليتي كتغير شي حاجة فـ 'الموافقة' وكتلقى 'الطلب' خسر بلا سبب، حيت الكلاصات داخلين فبعضياتهم بزاف. هنا فين كاين المشكل ديال كيفاش تحدد فين كيسالي موديل ويبدا موديل آخر.

## التماسك (Cohesion) والارتباط (Coupling)
الحدود ديال الموديلات ماشي هي غير تقسم الدوسيات، ولكن هي تجمع الحوايج اللي عندها علاقة ببعضياتها. التماسك العالي (High Cohesion) كيعني أن كلشي وسط الموديل خدام على هدف واحد. والارتباط الضعيف (Low Coupling) كيعني أن الموديلات مكيتحتاجوش بعضياتهم بزاف. إلا بدلتي معلومة فـ `Request` ولقيتي راسك خاصك تبدل الكود فـ `Buyer` service، عرف بلي الحدود ديالك غالطين.

## حدود مبنية على الدومين (Domain-Driven)
بلاصة ما تقسم الكود بطريقة تقنية (بحال services و repositories)، قسمو على حسب الخدمة اللي كيقدم. فالتطبيق ديالنا، نقدروا نقسموه لـ 3 ديال الموديلات:
1. **موديل الطلبات (Request Module)**: كيتكلف بصيفط الطلب والتأكد منو.
2. **موديل الموافقة (Approval Module)**: كيتكلف بـ workflow والموافقة ديال المدير.
3. **موديل الشراء (Ordering Module)**: كيتكلف بالتعامل مع الفورنيسورات.

## مثال تطبيقي
شوف مثلا كيفاش الطلب كيولي كوموند. بلاصة ما `RequestService` يعيط نيشان لـ `OrderService.create()`، كنستعملو واحد الطريقة باش نحافظو على الحدود.

```java
// فـ Request Module
public class RequestService {
    public void finalizeRequest(Long requestId) {
        // لوجيك باش نردوا الطلب مقبول
        // كنصيفطو حدث: RequestApprovedEvent
    }
}

// فـ Ordering Module
public class OrderListener {
    public void onRequestApproved(RequestApprovedEvent event) {
        // لوجيك باش نكرييو bon de commande
    }
}
```
بهاد الطريقة، الموديل ديال الطلبات مكيحتاجش يعرف كيفاش خدام الموديل ديال الشراء. الحدود هنا باينة ونقية.

## غلط شائع: وهم الـ Interface
بزاف ديال المطورين كيسحاب ليهم بلي إلا داروا interface بين جوج كلاصات، راه حيدوا الارتباط (coupling). هادشي غلط. إلا كانت `ApprovalInterface` كتحتاج object ديال `Request` اللي مرتبط بزاف بالتفاصيل الداخلية ديال `RequestModule` ، راه باقي عندك ارتباط قوي. الحدود كتكون ناجحة غير إلا كانت المعلومات اللي كتدوز بيناتهم بسيطة وواضحة.

## تمرين تطبيقي
**الوضعية**: عندك موديل واحد فيه 'بروفايل المستخدم' و 'طرق الدفع'. المستخدمين كيبدلو البروفايل ديالهم بزاف، ولكن طرق الدفع مكاتبدلش بزاف ومحتاجة سيكوريتي عالية. واش خاصهم يبقاو فموديل واحد؟

**الجواب**: لا، خاصهم يتفصلو. حيت كل واحد فيهم عندو سرعة تغيير مختلفة (volatility) ومتطلبات سيكوريتي مختلفة، يعني ماكاينش بيناتهم تماسك (cohesion).
