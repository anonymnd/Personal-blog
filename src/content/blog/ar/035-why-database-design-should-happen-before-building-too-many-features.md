هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخايل راسك خدام على App ديال الشراء (Procurement). بديتي بصاوب Feature فين المستخدم كيدير طلب (Request). كلشي داز مزيان. من بعد، بغيتي تزيد Feature ديال موافقة المدير (Manager Approval). هنا اكتشفتي بلي الطلب واحد يقدر يحتاج موافقة ديال بزاف ديال المديرين من أقسام مختلفة. حيت ما صممتيش Database في الأول، لقيتي راسك داير غير Column واحد سميتو `manager_id`. دابا خاصك تعاود الكود كامل وتدير Migration للبيانات غير باش تطبق قاعدة بسيطة ديال الخدمة.

## الثمن ديال التعديل من بعد
ملي كتخلي الـ Features هي اللي تحكم في الـ Database، كتسالي بطابلوات (Tables) مسطحة ما كتحملش التعقيد. في منهجية Merise، كنستعملو MCD (Modèle Conceptuel des Données) باش نحددو Entities و Relations قبل ما نقيسو الكود. إلا نسيتي هاد المرحلة، غتغلط في الـ Cardinality. مثلا، إلا كان Buyer واحد كيجير بزاف ديال Orders، ولكن Order واحد تابع لـ Buyer واحد، هاد العلاقة 1:N خاصها تكون واضحة من الأول. باش تحول علاقة من 1:1 لـ 1:N من بعد، خاصك تزيد Tables ديال الربط وتعدل كاع لي Query اللي في App.

## التعامل مع العلاقات المعقدة
بزاف ديال المبتدئين كينساو بلي العلاقة براسها تقدر تكون عندها معلومات. مثلا، إلا بغيتي تعرف *فوقاش* المدير وافق على الطلب، ما تقدرش دير هاد التاريخ في Table ديال Request (حيت هو اللي تـوافق عليه) ولا في Table ديال Manager (حيت هو كيوافق على بزاف د الحوايج). هنا خاصك Table ديال الربط (Join Entity).

```sql
-- مثال بسيط: Table ديال الربط للموافقات
CREATE TABLE request_approval (
    request_id INT,
    manager_id INT,
    approval_date DATE,
    status VARCHAR(20),
    PRIMARY KEY (request_id, manager_id)
);
```

## غلط شائع: 'Table ديال كلشي'
واحد الغلط كيديروه بزاف هو كيصاوبو Table وحدة كبيرة باش يهربو من الـ Joins. مثلا، كيديرو معلومات المستخدم (User) والمعلومات ديال الشركة (Organization) في Table وحدة سميتها `users`. هادشي كيولي مشكل ملي المستخدم كيولي ينتمي لأكثر من شركة. الحل هو نديرو Membership model: نفرقو بين `User` و `Organization` ونربطوهم بـ Table سميتها `Membership`.

## تمرين تطبيقي
السيناريو: الـ App ديالك دابا خاصها تسمح بلي Request واحد يكون فيه بزاف ديال السلع (Items).

السؤال: إلا كانت Table ديال `requests` فيها Column سميتو `product_id` ، علاش هادشي غلط وشنو هو الحل؟

الجواب: حيت هاد التصميم كيخلي كل طلب يكون فيه غير سلعة وحدة، واخا بزاف ديال الطلبات يقدرو يشيرو لنفس السلعة. الحل هو نحيدو `product_id` من `requests` ونصاوبو Table جديدة سميتها `request_items` باش نديرو علاقة 1:N.
