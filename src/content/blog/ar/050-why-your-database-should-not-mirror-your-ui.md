تخايل راسك خدام على تطبيق ديال المشتريات (procurement app). الـ UI فيها واحد الفورمير ديال 'طلب' (Request Form) فين المستخدم كيكتب سميتو، القسم ديالو، وليستة ديال السلع. المبتدئين غالباً كيديرو غلط هو يصاوبو جدول واحد سميتو `Request` فيه كولون ديال `requester_name` و `department_name`. هادشي غلط كبير حيت هنا راك كتقلد الشاشة فـ الـ Database.

## فرق بين تبديل الواجهة وتبديل قواعد الخدمة
إلا بدلتي ترتيب الحقول، زدتي dashboard ولا غيرتي filtre، غالبا خاصك تبدل العرض ولا query، ماشي النموذج ديال البيانات. ولكن قاعدة جديدة تقدر تحتاج تبديل schema بصح: إلا وليتي كتسمح بجوج ديال الناس يدفعو نفس الطلب، راه بدلتي العلاقة، واخا بان التغيير غير فـ formulaire. الهدف هو تخزن الحقائق وقواعد الخدمة، ماشي تبقى database عمرها ما تتبدل.
## الفرق بين الموديل المفاهيمي والفيزيائي
فـ المنهجية ديال Merise، كنفرقو بين الـ MCD (Modèle Conceptuel des Données) والـ Physical Model. الـ MCD كيركز على قواعد البيزنس (business rules) ماشي على الشاشات. مثلاً، 'المستخدم' هو entity، و 'القسم' entity أخرى. العلاقة بيناتهم هي قاعدة بيزنس (المستخدم تابع لقسم واحد)، وخا يكونوا بجوج فـ شاشة وحدة.

## مثال تطبيقي: طلبات المشتريات
بلاصت ما نديرو جدول واحد مسطح، كنخدمو بالـ normalization.

**غلط (مراية ديال UI):**
جدول `Requests`: `id`, `item_name`, `requester_name`, `dept_name`.

**صحيح (Normalized):**
- جدول `User`: `id`, `full_name`
- جدول `Department`: `id`, `dept_name`
- جدول `Request`: `id`, `user_id` (FK), `dept_id` (FK), `date`
- جدول `RequestItem`: `id`, `request_id` (FK), `product_name`, `quantity`

بهاد الطريقة، إلا تبدلات الـ UI لـ dashboard كيبين الطلبات على حساب القسم، الـ Database ما كتقيسهاش؛ غير كنبدلو الـ SQL JOIN.

## غلط شائع: تخزن السمية غير حيت كتظهر فالواجهة
إلا بغيتي المعلومات الحالية ديال الموظف، خزن ID ديال المدير وخلي backend يجيب السمية ويحطها فـ response DTO. المتصفح كيعرض هاد الرد؛ ما خاصوش يقلب مباشرة فـ tables. أما snapshot تاريخي مقصود فراه حاجة أخرى: فاتورة تقدر تحتافظ بسمية المورد كيف كانت نهار تصاوبات. حدد واش الحقل كيمثل معلومة حالية ولا حقيقة تاريخية قبل ما تختار normalization ولا snapshot.
## تمرين تطبيقي
سيناريو: الـ UI فيها صفحة 'مشروع' (Project) كيبان فيها ليستة ديال 'المهام' (Tasks) والموظف اللي مكلف بكل وحدة.

سؤال: واش خاصنا نزيدو `employee_name` فـ جدول `Tasks`؟

**الجواب:** لا. خاصنا نزيدو `employee_id` كـ foreign key. السمية بلاصتها فـ جدول `Employee` باش نتفاداو التكرار ومشاكل التحديث.
