هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخيل راسك كتقلب على واحد الطلب ديال شراء (purchase request) فـ تطبيق فيه 10 آلاف سطر. إلا ما كانش عندك index، لاباز دو دوني غدير 'Sequential Scan'، يعني غتبقى تقرا سطر بسطر من الأول حتى لآخر سطر باش تلقى داك الـ ID. هادشي كياخد وقت بزاف وكيثقل السيرفر. الـ B-Tree index كيحل هاد المشكل حيت كينظم الداتا على شكل شجرة متوازنة، وهادشي كيخلي لاباز دو دوني تنقز على أغلبية الداتا وتوصل نيشان للي بغات.

## شجرة متوازنة وعندها بزاف ديال الفروع
B-tree هي بنية متوازنة ديال البحث، وكل page تقدر يكون عندها بزاف ديال الفروع، ماشي غير جوج بحال binary tree. Root كتوجه البحث نحو pages داخلية ومن بعد نحو leaves. التوازن كيخلي عدد المستويات قليل حتى إلا كبر index. ولكن ماشي كل query غتاخد نفس الوقت؛ cache، شحال من نتيجة، والوصول لأسطر table حتى هوما كيأثرو.
## كنضيقو النطاق فكل خطوة
تخيل page مبسطة فيها الفواصل 25 و50 و75. إلا قلبنا على 42، كنمشيو للفرع اللي فيه القيم بين 25 و50. Page اللي من بعد كتعاود تضيق النطاق حتى نوصلو لـ leaf فيها النتائج. Pages الحقيقية غالبا فيها مفاتيح أكثر من هاد المثال التعليمي. والترتيب كيساعد حتى فـ range search، بحال الطلبات من 40 حتى 60، ماشي غير البحث بالمساواة.
## مثال: البحث على الطلبات
نفترض table ديال requests كاينة وفيها id وcreated_at. هاد index التوضيحية تقدر تعاون مع filtre ديال التاريخ:

```sql
CREATE INDEX requests_created_at_idx ON requests (created_at);

EXPLAIN
SELECT id, created_at
FROM requests
WHERE created_at >= DATE '2026-10-01';
```

قرا plan اللي اختارو database وما تخترعش نتيجة ديال التوقيت. Filtre كتخرج غير شوية ديال الأسطر تقدر تستافد من index؛ ولكن filtre كتجيب تقريبا table صغيرة كاملة تقدر تكون أرخص بـ sequential scan. PostgreSQL كيشوف statistics والتكلفة المتوقعة. Leaf entries غالبا كتشير لأسطر table؛ بعض queries اللي المعطيات ديالها مغطاة فـ index تقدر تستعمل index-only scan وتتفادى الوصول العادي للـ heap.
## غلط شائع: كثرة الـ Indexes
بزاف ديال الناس كيغلطو وكيضيفو index لكل كولون باش 'كلشي يولي سريع'. ولكن خاصك تعرف أن أي `INSERT` أو `UPDATE` كديرها، لاباز دو دوني خاصها تعاود تحدد الـ B-Tree. إلا كترتي من الـ indexes، عمليات الكتابة غتولي ثقيلة وغتستهلك مساحة كبيرة فـ الديسك.

## تمرين تطبيقي
زدتي index ولكن EXPLAIN باقي كيبين Seq Scan فـ table صغيرة. واش هادشي ضروري كيعني index خاسرة؟

**الجواب:** لا. Planner يقدر يلقى قراءة table مباشرة أرخص. شوف predicate، شحال من سطر كتخرج، statistics، وحجم بيانات قريب للاستعمال الحقيقي. Index غير طريق ممكنة للبحث، ماشي أمر كيحتم على أي query تستعملها.
