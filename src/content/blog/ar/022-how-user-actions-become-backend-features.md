هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

بزاف ديال المطورين كيبداو يكتبو الكود غير كيسمعو طلب بحال 'بغيت نطلب بيسي جديد'. هاد الطريقة كتخلينا نساو حالات مهمة، بحال مثلا يلا كان المدير في عطلة أو الميزانية سالات. الفرق بين شنو كيدير المستخدم وبين الـ feature في الـ backend هو فين كاين الـ business logic.

## الفرق بين الـ Actor والـ User
قبل ما تبدا تكودي، خاصك تفرق بين الـ Actor والـ User. الـ Actor هو الدور (مثلا: Requester, Manager, Buyer) اللي كيتعامل مع السيستيم. أما الـ User فهو الشخص اللي داخل بالحساب ديالو. والـ domain entity هي الحاجة اللي كنخدمو عليها، بحال 'PurchaseRequest'. يلا مفرقتيش بيناتهم، تقدر تطيح في مشكل ديال الصلاحيات (Authorization)، مثلا شي واحد يوافق على الطلب ديالو راسو.

## كيفاش نرسمو طريق العملية
باش تحول تصرف لـ feature، خاصك تشوف 'الطريق الساهلة' (Happy Path) و 'طرق المشاكل' (Unhappy Paths). في تطبيق ديال المشتريات، عملية 'صيفط طلب' ماشي هي غير تزيد سطر في لاباز دو دوني. خاصك تأكد واش هاد الشخص تابع لقسم صحيح، واش هاد المادة مسموح بها. وطرق المشاكل هي مثلا 'الطلب ترفض حيت الميزانية ما كافياش'.

## مثال تطبيقي: ميزة الموافقة (Approval)
نشوفو هاد التصرف: 'المدير كيوافق على طلب'.

**المنطق ديالها:**
1. السيستيم كيتأكد واش الـ Actor هو 'Manager'.
2. السيستيم كيشوف واش هاد المدير هو المسؤول على هاد الطلب بالضبط.
3. السيستيم كيبدل الحالة من `PENDING` لـ `APPROVED`.

```java
// مثال بسيط على المنطق ديال الموافقة
public void approveRequest(Long requestId, User manager) {
    PurchaseRequest request = repository.findById(requestId);
    if (!manager.getRole().equals(Role.MANAGER)) {
        throw new UnauthorizedException("غير المديرين اللي يقدروا يوافقوا");
    }
    if (!request.getSupervisor().equals(manager)) {
        throw new BusinessException("أنت ماشي هو المسؤول على هاد الطلب");
    }
    request.setStatus(Status.APPROVED);
    repository.save(request);
}
```

## غلط شائع: نسيان القيود (Constraints)
واحد الغلط كيديروه بزاف هو كيركزو غير على 'شنو غيوقع' (تبديل الحالة) وكينساو 'كيفاش' (non-functional constraints). مثلا، خاص الموافقة تكون في أقل من 48 ساعة، أو خاص السيستيم يسجل شكون وافق باش يكون عندنا أثر (Audit). باش تصلح هادشي، زيد فقرة ديال 'القيود' في الورقة ديال المتطلبات قبل ما تبدا الكود.

## تمرين تطبيقي
**السيناريو:** المشتري (Buyer) كيعلم بلي الطلب 'تطلب' (Ordered). شنو هي حالة وحدة من 'طرق المشاكل' (unhappy path) لهاد العملية؟

**الجواب:** يقدر يكون المدير لغى الطلب في الوقت اللي المشتري كان حال الصفحة وقبل ما يورك على زر 'Order'.
