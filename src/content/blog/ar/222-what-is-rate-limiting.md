هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخيل عندك تطبيق ديال الشراء (procurement app) فين الموظفين كيصيفطو طلبات. فجأة، واحد السكريبت فيه غلط بدا كيصيفط 10,000 طلب فالثانية لـ `/submit-request`. القاعدة ديال البيانات (database) غتتبلوكا، والمدير ما غيقدرش يوافق على حتى طلب، والسيستيم كامل غيطيح. هنا فين كنحتاجو الـ Rate Limiting: باش نحميو السيرفيس ديالنا من كثرة الطلبات اللي تقدر تقتلو.

## كيفاش كيخدم الـ Rate Limiting
الـ Rate Limiting هي واحد الطريقة كنحددو بيها شحال من طلب يقدر يصيفط مستخدم واحد أو IP واحد فواحد الوقت محدد. كيكون بحال شي عساس فالباب ديال التطبيق. ملي كتوصل طلب، السيستيم كيشوف واش هاد المستخدم فات الحد المسموح ليه. إلا كان فاتو، السيرفر كيرفض الطلب وكيرجع كود HTTP 429 اللي كيعني "Too Many Requests".

## الفرق بين L4 و L7
على حسب فين بغيتي دير هاد التحديد، عندك جوج خيارات. الـ L4 (Transport level) كيكون فـ TCP/UDP، وكيركز غير على الـ IP. هو سريع بزاف ولكن ما كيعرفش شنو كاين وسط الطلب. أما الـ L7 (Application level) كيكون فـ HTTP، وهنا تقدر تحدد الطلبات على حساب الـ API key، أو ID ديال المستخدم، أو حتى endpoint محدد بحال `/order-payment`.

## الخوارزميات اللي مستعملة (Algorithms)
كل حالة وعندها خوارزمية. الـ **Token Bucket** كيسمح بشوية ديال "الزحام" (bursts)؛ المستخدم كيجمع tokens وكيقدر يخدمهم دقة وحدة. الـ **Leaky Bucket** كيكون صارم كثر، كيخرج الطلبات بواحد الريتم ثابت ومنتظم. أما الـ **Fixed Window** كيبدا يحسب من جديد فواحد الوقت محدد (مثلا كل ساعة)، ولكن المشكل ديالو هو أنه يقدر يدوز الدوبل ديال الترافيك فاش كتسالي النافذة وتبدا وحدة جديدة.

## مثال تطبيقي: API ديال الشراء
نفترضو بغينا نحددو الـ endpoint ديال `/approve-request` فـ 5 ديال الطلبات فالدقيقة لكل مدير، باش نتفاداو الغلط ديال الضغط على الزر بزاف المرات.

```java
// مثال بسيط كيفاش كيكون التشيك
public Response handleApproval(Request req) {
    String managerId = req.getUserId();
    if (rateLimiter.isExceeded(managerId, 5, Duration.ofMinutes(1))) {
        return Response.status(429).entity("غير بشوية عليك أ مدير!").build();
    }
    return procurementService.approve(req.getId());
}
```
النتيجة: إلا مدير ورك على "Approve" 6 المرات فـ 30 ثانية، الطلب السادس غيتحبس ديك الساعة، وهكدا كنحمو الـ database من الخدمة الزايدة.

## غلط شائع: Local vs Distributed State
بزاف ديال الناس كيغلطو وكيخزنو عدد الطلبات فـ variable وسط الكود ديال السيرفر. إلا كان عندك 3 ديال السيرفرات، المستخدم يقدر يصيفط 3 المرات كثر من الحد المسموح حيت كل سيرفر كيحسب بوحدو. باش تحل هاد المشكل، خاصك تستعمل شي حاجة مشتركة بحال Redis باش كاع السيرفرات يشوفو نفس الحساب.

## تمرين تطبيقي
إلا كان السيستيم خدام بـ Leaky Bucket والسرعة ديال الخروج هي 2 طلبات فالثانية، شنو غيوقع إلا مستخدم صيفط 10 ديال الطلبات فثانية وحدة؟

**الجواب:** 2 طلبات غيدوزو ديك الساعة، و 8 اللي بقاو يا إما يتسناو فـ queue (إلا كان السطل باقي ما عمرش) يا إما يتلغاو فالبلاصة إلا كان السطل عامر.
