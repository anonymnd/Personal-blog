تخايل معايا خدام على app ديال procurement (المشتريات). واحد manager بغا يبدل الحالة ديال طلب شراء من 'Pending' لـ 'Approved'. واش خاص الـ API تصيفط الطلب كامل للسيرفر، ولا تصيفط غير هاديك الحالة لي تبدلات؟ هنا فين كاين الفرق بين PUT و PATCH.

## كيفاش خدام PUT
PUT مديور باش يعوض (Replace). ملي كتصيفط PUT، بحال كتقول للسيرفر: "هاك هاد النسخة الجديدة، حيد لي كاين ف هاد العنوان (URI) ودير بلاصتو هادشي لي صيفطت". إلا كانت الـ resource كاينه، كتمسح وكيدار بلاصتها الجديدة. وإلا ما كانتش، كاين لي كيخلي PUT تكرييها. أهم حاجة ف PUT هي أنها idempotent: يعني واخا تصيفط نفس الطلب 10 د المرات، النتيجة النهائية ف السيرفر غتبقى هي هي.

## كيفاش خدام PATCH
PATCH مديور غير للتعديلات الجزئية (Partial updates). بلا ما تصيفط الـ object كامل، كتصيفط غير داكشي لي تبدل. هاد الطريقة حسن ف الـ performance خصوصاً إلا كان الـ object كبير. ولكن PATCH ماشي ديما idempotent. مثلاً، إلا كان PATCH كيزيد عنصر لواحد la liste، إلا عاودتي الطلب بزاف د المرات، غادي يبقى يزيد نفس العنصر كل مرة، وهكا الحالة ديال السيرفر كتبدل.

## مثال تطبيقي: طلب شراء
تخايل عندنا طلب بحال هكا: `{ "id": 101, "item": "Laptop", "qty": 1, "status": "Pending" }`.

**بـ PUT:**
باش تبدل الكمية (qty) لـ 2، خاصك تصيفط كلشي:
`PUT /requests/101` 
`{ "id": 101, "item": "Laptop", "qty": 2, "status": "Pending" }` 
النتيجة: السيرفر كيبدل السطر القديم كامل بهاد النسخة الجديدة.

**بـ PATCH:**
باش تبدل الكمية لـ 2، كتصيفط غير لي تبدل:
`PATCH /requests/101` 
`{ "qty": 2 }` 
النتيجة: السيرفر كيبدل غير `qty` وكيخلي داكشي لاخر كيفما كان.

## غلط شائع: PUT ناقصة
بزاف د الناس كيستعملو PUT ولكن كيصيفطو غير الحقول لي تبدلو. إلا كان السيرفر متبع المعايير ديال REST بدقة، طلب PUT فيه غير `{ "qty": 2 }` يقدر يمسح `item` و `status` ويرجعهم null، حيت PUT كتعوض كلشي. باش تفادى هاد المشكل، استعمل PATCH للتعديلات البسيطة، ولا جيب الـ object كامل عاد صيفطو بـ PUT.

## تمرين تطبيقي
سيناريو: بغيتي تبدل غير الـ email ديال مستخدم ف بروفيل فيه 50 معلومة مختلفة. شنو هي أحسن طريقة وعلاش؟

**الجواب:** PATCH، حيت باش تصيفط 49 معلومة ما تبدلاتش بـ PUT غادي يكون ضياع ديال الـ data وغادي تزيد من احتمال أنك تمسح شي حاجة بالغلط.

## العقد ديال API، ماشي تبديل السطر كامل
PUT كيبدل representation اللي محددة فـ API contract، ماشي كل column فـ database. الحقول اللي كيحسبها السيرفر ماشي بالضرورة خاص المستخدم يصيفطها. Idempotency كتعني النتيجة المقصودة؛ logs يقدرو يسجلو كل محاولة. إلا كانو تعديلات فـ نفس الوقت، PUT وPATCH بجوج يقدرو يحتاجو version check، بحال ETag مع `If-Match`، باش ما يضيعش تعديل ديال شي واحد.
