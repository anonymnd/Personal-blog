هاد الأمثلة غير باش نفهمو الفكرة؛ الإعدادات ديال التطبيق وبعض التعريفات المساعدة ممكن ما يكونوش مكتوبين.

تخيل راسك كاتصاوب سيستيم ديال الشراء (procurement). فاش كاتكتب المتطلبات، كاتكتب «المدير» (Manager). ولكن هنا خاصك تحبس وتفكر: واش هاد المدير هو شخص جالس قدام الشاشة، ولا هو دور (role) عنده صلاحيات، ولا هو غير سطر ديال البيانات فـ base de données؟ إلا خلطتي بين هاد التلاتة، الكود ديالك غادي يولي معقد وصعيب تبدلو من بعد.

## الـ Actor (الفاعل)
الـ Actor هو أي حاجة *برا* السيستيم كاتفاعل معاه. الـ Actor هو «دور» ماشي شخص محدد. مثلاً، «المُطالب» (Requester) هو Actor. ومشي ضروري يكون بنادم؛ حتى شي API ديال المحاسبة اللي كاتصيفط تأكيد الخلاص كاتعتبر Actor. الـ Actors هما اللي كيقولو لينا *شكون* ولا *شنو* اللي بدا العملية.

## الـ User (المستخدم)
إلى كان الـ Actor هو الدور، الـ User هو الحساب (account) اللي داخل للسيستيم. الـ User هو اللي كيربط الشخص الحقيقي بالبرنامج. واحد الـ User يقدر يلعب بزاف ديال الأدوار (Actors). مثلاً، «أحمد» هو User، يقدر يكون «مُطالب» باش يشري بي سي، وفي نفس الوقت يكون «مدير» باش يوافق على الطلبات ديال الفريق ديالو.

## الـ Entity (الكيان)
الـ Entity هي حاجة ديال البيزنس عندها هوية (ID) خاصة بها وكاتبقى كاينة واخا يتبدل الوقت. عكس الـ User اللي كيهتم بالدخول (access)، الـ Entity كتهتم بالخدمة (business logic). فالتطبيق ديالنا، «طلب الشراء» (`PurchaseRequest`) هو Entity. عنده ID، حالة (status)، وثمن. واخا الـ User اللي دار الطلب يخرج من الخدمة، الـ Entity ديال الطلب كتبقى مسجلة.

## مثال تطبيقي: عملية الموافقة
شوف هاد المثال كيفاش كيكون فـ Java:

```java
// Entity: الشيء اللي كنخدمو عليه
public class PurchaseRequest {
    private Long id;
    private String item;
    private RequestStatus status;
    // Getters and setters
}

// Logic: كنقلبو واش الـ User عنده دور الـ Actor المناسب
public void approveRequest(User user, PurchaseRequest request) {
    if (!user.hasRole("MANAGER")) {
        throw new UnauthorizedException("غير المدير اللي يقدر يوافق");
    }
    request.setStatus(RequestStatus.APPROVED);
}
```
النتيجة: السيستيم كيتأكد من الدور ديال الـ User (Actor) عاد كيغير الحالة ديال الـ Entity.

## غلط شائع: تخلط الـ User مع الـ Entity
بزاف ديال المبرمجين كيديرو غلط ديال يحطو معلومات الخدمة (بحال القسم أو سقف الميزانية) وسط الـ User object. هادشي غلط حيت إلا تبدل القسم ديال الموظف، كاتمحي المعلومة القديمة. الحل هو تصاوب Entity سميتها `EmployeeProfile` وتربطها بالـ User.

## تمرين تطبيقي
فـ سيستيم فين «المشتري» (Buyer) كيدوز كوموند بناءً على طلب مقبول، حدد شكون هو الـ Actor، الـ User، والـ Entity.

**الجواب:** الـ Actor هو المشتري (Buyer)؛ الـ User هو الشخص اللي مكونيكطي (مثلاً سارة)؛ والـ Entity هي الطلبية (Order).
