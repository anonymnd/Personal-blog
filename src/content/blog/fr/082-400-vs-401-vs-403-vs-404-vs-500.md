Imaginez que vous développez une application d'achats. Un demandeur tente de soumettre une demande d'achat, mais le serveur renvoie une erreur générique. Sans codes d'état spécifiques, le frontend ne sait pas si l'utilisateur a oublié un champ, s'il n'est pas connecté ou si la base de données a planté. Cette ambiguïté nuit à l'expérience utilisateur et ralentit le débogage.

## Erreurs Client (4xx)

Les codes HTTP 4xx indiquent que le client a envoyé une requête que le serveur ne peut pas traiter. Le plus courant est le **400 Bad Request**, utilisé lorsque le corps de la requête est syntaxiquement incorrect. Par exemple, si l'application attend une `quantité` numérique mais reçoit la chaîne "dix", un 400 est approprié.

**401 Unauthorized** et **403 Forbidden** sont souvent confondus. Un 401 signifie que le serveur ne sait pas qui vous êtes (authentification). Il inclut généralement un en-tête `WWW-Authenticate`. Un 403 signifie que le serveur sait qui vous êtes, mais que vous n'avez pas la permission (autorisation). Dans notre application, un demandeur peut être authentifié (200 OK) mais interdit (403) d'approuver sa propre demande.

**404 Not Found** survient lorsque la ressource demandée n'existe pas. Cependant, certaines API renvoient un 404 au lieu d'un 403 pour masquer l'existence d'une ressource sensible.

## Erreurs Serveur (5xx)

Le **500 Internal Server Error** est l'erreur générique pour tout problème côté serveur qui n'est pas la faute du client. Cela peut être une exception `NullPointerException` non gérée dans le backend Java ou une perte de connexion à la base de données. Contrairement aux codes 4xx, un 500 indique que le serveur a échoué à traiter une requête valide.

## Exemple Concret : Flux d'Achats

Considérons le point de terminaison `PUT /requests/{id}/approve` :
- **Scénario A** : Le corps de la requête oublie le `managerId`. Résultat : `400 Bad Request`.
- **Scénario B** : Aucun jeton Bearer n'est fourni dans l'en-tête. Résultat : `401 Unauthorized`.
- **Scénario C** : Un employé simple tente d'appeler l'endpoint d'approbation. Résultat : `403 Forbidden`.
- **Scénario D** : L'ID de demande `999` n'existe pas. Résultat : `404 Not Found`.
- **Scénario E** : Le serveur lance une `RuntimeException` lors de la mise à jour. Résultat : `500 Internal Server Error`.

## Erreur Courante : 401 vs 403

Une erreur fréquente consiste à renvoyer un 401 alors que l'utilisateur est connecté mais n'a pas les droits nécessaires.
*Correction* : Utilisez 401 uniquement pour des identifiants manquants ou invalides. Utilisez 403 quand l'identité est vérifiée mais l'action est interdite.

## Exercice Pratique

Si un utilisateur tente d'accéder à `/orders/55` mais qu'il n'est pas du tout connecté au système, quel code d'état l'API doit-elle renvoyer ?

**Réponse** : 401 Unauthorized.
