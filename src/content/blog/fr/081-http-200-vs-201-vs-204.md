Ces exemples illustrent le concept ; la configuration de l’application et les définitions auxiliaires peuvent être omises.

Imaginez que vous développez un système d'approvisionnement. Un demandeur soumet une demande d'achat et votre API renvoie un message de succès. Mais ce 'succès' signifie-t-il que la demande a simplement été reçue, qu'un nouvel enregistrement a été créé, ou qu'une mise à jour a eu lieu sans avoir besoin de renvoyer de données ? Utiliser un code 200 OK générique pour tout rend difficile pour le frontend de savoir s'il doit rediriger l'utilisateur ou simplement rafraîchir une liste.

## Comprendre le HTTP 200 OK
Le HTTP 200 est la réponse standard pour les requêtes HTTP réussies. Il est le plus souvent utilisé avec les requêtes GET pour renvoyer la représentation d'une ressource, ou avec les requêtes PUT/PATCH lorsque le serveur renvoie l'objet mis à jour. Il indique au client : "J'ai traité votre requête, et voici le résultat."

## La spécificité du HTTP 201 Created
Alors que le 200 signifie 'OK', le 201 signifie spécifiquement 'Créé'. Il est principalement utilisé avec les requêtes POST. Lorsqu'un demandeur soumet une nouvelle demande d'achat dans notre application, le serveur ne dit pas seulement OK ; il confirme qu'une nouvelle ressource existe. Idéalement, une réponse 201 inclut un en-tête `Location` pointant vers l'URL de la ressource créée.

## Le silence du HTTP 204 No Content
Le HTTP 204 est utilisé lorsqu'une requête réussit, mais qu'il n'y a aucune représentation à renvoyer au client. C'est courant pour les requêtes DELETE ou les mises à jour PUT où le client possède déjà les données et n'a pas besoin que le serveur renvoie le même objet. Cela économise de la bande passante en omettant totalement le corps de la réponse.

## Exemple pratique : Flux d'approvisionnement

| Action | Méthode | Code attendu | Raison |
| :--- | :--- | :--- | :--- |
| Voir demande | GET | 200 OK | Retourne les détails |
| Soumettre demande | POST | 201 Created | Nouvel enregistrement créé |
| Modifier statut | PATCH | 204 No Content | Statut changé, pas de corps requis |

```http
POST /api/purchase-requests
Content-Type: application/json

{"item": "Laptop", "qty": 1}

HTTP/1.1 201 Created
Location: /api/purchase-requests/123
```

## Erreur courante : L'abus du 200 OK
Les développeurs utilisent souvent le 200 OK pour tout. Par exemple, renvoyer 200 après une création POST au lieu de 201. Cela oblige le client à analyser le corps de la réponse pour déterminer si une ressource a réellement été créée, au lieu de s'appuyer sur la sémantique du code de statut HTTP.

## Exercice pratique
Quel code de statut l'action 'Approuver' d'un manager devrait-elle renvoyer si l'API met à jour le statut de la demande en 'Approuvé' mais ne renvoie pas l'objet mis à jour dans le corps ?

**Réponse :** 204 No Content.
